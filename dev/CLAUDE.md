# One-A-Day — Build Spec for Claude Code

## Product Vision — the north star
`~/Downloads/ONE-A-DAY — PRODUCT VISION & DESIGN DOCUMENT.pdf` (v1.7, May 29 2026) is the actual product vision: an AI executive assistant, not a to-do app — "You came for a to-do app. You found something bigger." Its core discipline is **epistemic auditing**: continuously tracing every rule, task, and stopping condition back to whether it's verified fact or an unexamined assumption. Current codebase terminology maps to vision terminology as follows — use this when either document references the other:

| Vision term | This codebase | Status |
|---|---|---|
| Active Threads (closing condition, current assumption audit, next action + contingency, evolution log, graph edges) | `Thread` (`js/models.js`), `js/data.js` | LIVE — the vision's fields are this app's actual `Thread` schema, close to 1:1 |
| The graph / cross-area edges / cycle detection | `connections`/`edge_type`, `OAD.Models.Graph.detectCycles` | LIVE |

| Idea Incubation (conversational review loop: Activate/Keep incubating/Let go) | `Idea` (`js/models.js`), `renderIdeaPanel` | PARTIAL — ideas exist as a first-class layer; the *conversational* resurfacing loop isn't built, ideas are reviewed by browsing the panel, not surfaced proactively |
| The One Annoying Thing | `OAD.getDailyToat()` (TOAT) | LIVE |
| The Heat Map ("primary navigation surface") | `OAD.getLifeAreaHeat()` | PARTIAL — the data exists (avg pressure per life area) and renders as a strip on the dashboard, but it is not the primary navigation surface the vision describes (no cycles/undefined-closing-condition/cross-area-heat overlay) |
| The Connection Engine (proactive, existing-node-to-existing-node) | ADE — `OAD._ade001/002/003` (`js/engine.js`) | LIVE, narrower than vision — ADE's 3 rules (sequential numbering, parent/child, shared identifier + prep→submit language) are real pattern-matching, not full "does this connect to 2+ nodes / is it meaningful / does it change what to do" epistemic testing |

| Localization: "no hardcoded copy anywhere in the codebase," prompts localized alongside UI | `OAD.Config.prompts.*` (all 5 AI prompt templates), `locales/en.json` | LIVE for AI prompts as of today; broader UI-string localization is partial (`OAD.t()`/`data-i18n` exist but not universally applied) |

## Phase 1 — built

- **`js/threadTemporalStatus.js`** — `OAD.TemporalStatus`, 7 pure functions (`isOverdue`, `isDueToday`, `isStalled`, `daysUntilDeadline`, `daysSinceNextActionDate`, `cardDateLabel`, `dataHygieneWarnings`), zero DOM references, zero hidden global state (confirmed by grep — only comments mention `Date.now()`/`console`, no real calls). `today` is a real `Date` object, not the ticket's implied bare string — deliberate: this app already has tested, deliberately-built time-of-day precision (`next_action_time`/`deadline_time`, e.g. "meet Amy at 09:30 today" must be overdue by 10am even though the date alone says "not yet"), which a bare date string can't express. A `Date` is a strict superset — "not hardcoded to `new Date()`" is satisfied by it being an explicit argument, not by its type.
- **`owner_id` schema hook** (`js/data.js`): `OAD.DEFAULT_OWNER_ID = 'default-owner'`, added to `OAD.makeThread`, backfilled in `_normalizeDB`, threaded through every `OAD.TemporalStatus` function as an optional 3rd argument (mismatched owner → the function's "safe negative": `false`/`null`/`'none'`/`[]`). Explicitly NOT redundant with Supabase's account-level RLS (a different, already-solved boundary) — this is a placeholder for a future *intra-account* scope (e.g. a shared team workspace), costing nothing today since every real thread shares one value. Confirmed round-trips correctly through export/import (verified against a live re-export).
- **`OAD.Config.temporalStatusStrings`** — all new user-facing copy this refactor introduced (card labels, "Past deadline"/"Past due," the masked-drift warning badge/tooltip) pulled from config, not inlined — caught and fixed two hardcoded strings (`'⚠ next action overdue'`) that slipped through on a first pass, confirmed via grep after the fix.
- **Migration — done via two strategies, not "rewrite everything":**
  1. **Direct migration** (the call site had its own duplicate logic): `OAD.Due.buckets()`'s overdue/today, `OAD.Due.stalledThreads()`, TOAT tiers 2/3 + `isFriction` (`js/data.js`), the thread-card "remaining" countdown in both `OAD.renderList` and `OAD.renderListView` (`js/render.js`, now via `cardDateLabel` + a visible `dataHygieneWarnings` badge when the drift-masking case applies — the actual ENV-125 fix, screenshotted), `getEisenhowerQuadrant`'s day-load helper and `OAD.calculateDayLoadScore`/`OAD.getDayLoad` (`js/models.js`/`js/engine.js`), the two AI prompt builders' today/stalled filters (`js/api.js` — see real bug found below), `OAD.focusReason`'s due-today check, `OAD.Due.selfCheck()`'s invariant check.

## Phase 2 — schema audit (reported before any schema change)

**The ticket's core premise was wrong, and this changed the whole phase's scope.** `closing_condition`/`closing_condition_type`/`closing_condition_met` and `current_assumption`/`assumption_verified` already exist in the schema (`OAD.makeThread`), fully wired into the Edit modal, thread detail view, search, and `_IMPORT_FIELDS` — not a partial implementation, complete plumbing. So Phase 2's real remaining work was only ever "backfill a few real examples," not "add fields + build UI."

- **A real, separate bug found and initially mis-fixed, then correctly reverted:** `OAD.exportThreads()` was missing `current_assumption` from its field map entirely — `assumption_verified` exported, the paired free-text field silently never did. First instinct was to add it as an obvious oversight fix. **This was wrong** — an existing, clearly-named test (`'moat-safe export strips proprietary attributes'`) explicitly asserts `current_assumption`, `contingency_action`, `contingency_escalation`, `evolution_log`, and `ai_insights` are *all* deliberately excluded from this export format, a coherent "operational state vs. internal reasoning trail" boundary, not an oversight. ## Data Model — Thread
Every thread has:
- **uuid** — stable UUID assigned at creation (`crypto.randomUUID()`). Used for export/import matching. Never changes. Backfilled by `_normalizeDB()` for threads that predate this field.
- id — sequential integer, internal use only
- **created_at** (ISO timestamp, LIVE) — set by `makeThread()` at creation. Legacy threads that predate this field backfill to `null` (unknown) in `_normalizeDB()` — never fabricated.
- title, life_area, status (`inbox|open|waiting|dormant|stalled|closed`), priority (critical|high|medium|low)
- closing_condition (string) — what verified OUTCOME closes this, not what action
- closing_condition_type (outcome|action), closing_condition_met (boolean)
- current_assumption (string), assumption_verified (boolean)
- next_action, next_action_date, **next_action_time** (optional 'HH:MM', LIVE), next_action_channel, next_action_contact
- contingency_trigger_date, contingency_action, contingency_escalation
- deadline (ISO date, optional), **deadline_time** (optional 'HH:MM', LIVE), effortEstimate, weeklyCommitment, effortLogged
- connections[] — graph edges: `{uuid, to_uuid, to_label, edge_type: blocks|enables|relates|blocked_by, auto_generated, rule, confidence, confirmed_by_user, created_at}`. Edges with `auto_generated: true` and `confirmed_by_user: false` are ADE-inferred, pending review.
- evolution_log[] — {date, note} living history
- ai_insights[] — counsel engine observations
- date_push_count (integer) — tracks how many times the next_action_date has been pushed back
- **dormant_trigger** (string) — condition-based re-engagement trigger, e.g. "Re-engage when SDVOSB certified". Only meaningful when status = dormant. Set in Edit Thread modal.
- **user_action_complete** (boolean, default false) — "I've done my part / ball in their court." Only meaningful when status = waiting. Auto-resets to false when status changes away from waiting. Set via checkbox in Edit Thread modal.

**Status semantics (ordered: inbox → open → waiting → dormant → stalled → closed):**
- `inbox` — raw, uncaptured/unreviewed idea (Quick Add, LIVE). Contributes **zero pressure**, excluded from Focus Now/TOAT/Daily View/Matrix aggregates and life-area heat, same treatment as `dormant`. Still visible via the List Tab's "All States" filter and Graph Views (both iterate `OAD.STATUSES` generically). No synthesis happens at capture — see `OAD.quickAddThread()`. Housekeeping review screen (batched triage of inbox items) is spec'd but not yet built.
- `open` — actively being worked
- `waiting` — action sent, waiting on someone else's response
- `dormant` — deliberately parked; no current value to offer; milestone-gated re-engagement. Contributes **zero pressure**. Never appears in TOAT or Focus Now.
- `stalled` — friction state; something is blocking this from moving
- `closed` — done

**Dormant vs Waiting distinction:** dormant = "I'm choosing not to engage yet" (self-imposed, milestone-gated). Waiting = "I've acted and am awaiting response" (time-sensitive, someone else has the ball).

**user_action_complete effect:** when `status = waiting` AND `user_action_complete = true`, pressure is multiplied by 0.35. Thread is excluded from Focus Now primary/secondary candidate pools — only surfaced as absolute last resort if nothing else qualifies. Thread detail shows "Ball in Their Court" info card.

## Focus Now — Date-Scoped Selection (LIVE)
Origin: reported directly — Focus Now surfaced a thread due in 5 days (pressure 69) over one due today (pressure 53), because `OAD.selectFocusThread()` (`js/engine.js`) sorted the *entire* active backlog by raw pressure with no date filter at all. "What should I focus on right now" was really "what's the single highest-pressure thread anywhere in the backlog, regardless of when it's due."

- **Fix**: candidates are now scoped to `next_action_date <= today` (today + overdue) *before* the existing blocked/waiting-actioned tiered waterfall runs, not after. The waterfall itself (primary: not blocked; secondary: allow blocked; last resort: allow waiting+actioned) is unchanged, just operating on the narrower, date-scoped pool.
- **`OAD.selectFutureFocusSuggestion()`** — when nothing is due today or overdue, returns the nearest upcoming item (nearest date first, tie-broken by pressure) as an optional "get ahead" suggestion — never presented as an actual recommendation.
- **`OAD._renderFocusNowEmptyState()`** (`js/render.js`) — shared by all three Focus Now card render sites (they were already duplicated pre-existing code; this was made a single function specifically so the empty-state markup can't drift out of sync across them the way the overdue-badge blocks once did). Mirrors TOAT's celebrate-when-empty style (green, 🎉) rather than showing a dead end, with the future suggestion appended below if one exists.
- **Existing tests updated**: several `selectFocusThread` tests predated date-scoping and used fixtures with no `next_action_date` at all — updated to include one, since real usage always has a next_action_date and the tests should reflect the now-intentional scoped behavior.

## Closure Wizard — Reopen No Longer Misfires (LIVE)
Origin: reported directly — reopening a closed thread (status: closed → open) with an active connection would incorrectly show the "you are closing this" dialog and attempt to walk/break that connection, instead of just saving the reopen.

Root cause, found in `_saveEditThread` (`js/modals.js`): `const isClosing = (data.status === 'closed' || data.closing_condition_met)` read the *submitted form state*, not the transition direction. The "Closing condition met" checkbox isn't wired to the Status dropdown — reopening a thread that was closed with `closing_condition_met: true` leaves that checkbox checked unless separately unchecked, so `isClosing` misfired true even though `data.status` was `'open'`. `OAD.needsClosureWizard()` then correctly found an active connection (it checks for any active connection, any edge type, by design — that part was never the bug) and opened the wizard for what should have been a plain reopen.

**Fix**: `isClosing = (...) && prev.status !== 'closed'` — only a genuine transition, or a closing_condition_met that's newly true this save, counts as closing. This also fixes a milder version of the same bug: previously, editing *any* field on an already-closed thread with active connections would re-trigger the closure wizard on every save, not just the moment it first closes.

## Cadences in Export/Import (LIVE)
Origin: filed spec, `CADENCE_EXPORT_IMPORT_SPEC.md` — "Cadences are a function of threads. They are not a parallel system that happens to also produce recurring obligations... whatever Cadences turn out to be under the hood, Export/Import's existing promise — 'ground truth for all threads, no exceptions' — has to actually cover them."

Step 0 (find out what Cadences actually are) resolved this as **Path B**: cadences live in their own `OAD.DB.cadences` array with their own shape (`OAD.makeCadence()`, data.js:280) — sequential integer `id`, no `uuid` field, not thread-shaped rows with a discriminator. `OAD.exportThreads()` had zero cadence handling.

- **Export**: `exportThreads()` adds a `cadences` array (full fields: `id`, `title`, `life_area`, `recurrence`, `days_of_week`, `last_completed`, `next_due`, `notes`, `consequences`) plus `cadence_count`, sibling to `threads`/`edges`.
- **Import matching**: cadences match on `id` — their real, stable identifier. No title-fallback (that exists for threads only to handle pre-uuid legacy formats; cadence export/import is brand new, so every row either carries a real `id` or is a genuine create). A create row's incoming `id` (if any) is ignored — `addCadence()` always assigns the real sequential id, same as the live "+ Add Cadence" UI, never fabricating an identity from the import file.
- **`OAD._CADENCE_IMPORT_FIELDS`** (data.js) governs which fields sync on update, mirroring `_IMPORT_FIELDS` for threads.

## Due Today — Child-Suppression Bug (LIVE)
Origin: investigation doc — "Due Today" showed 1-of-4, then later 0-of-2, ground-truth threads on two separate real-data snapshots.

Root cause, found in `renderTodayView()`/`renderDailyView()`/the third near-duplicate view (`js/render.js`): any thread with a `parent_uuid` pointing at another active thread gets added to `suppressedUUIDs` and filtered out of `filteredActive` — the pool every flat bucket (Overdue/Today/Week/Active) is built from — so it can instead be represented via a nested `childSummaryHtml` badge under its parent's row. That suppression was **unconditional** (aside from an existing Patient-life_area carve-out): it didn't check whether the parent would itself land in a visible bucket. Most parent/project threads have no `next_action_date` at all, so they never appear in Today/Overdue/Week either — meaning a child due today had nowhere to be nested under and simply vanished. The child-summary badge compounded this: it only counted overdue children (`children.filter(OAD.isActionOverdue)`), never due-today ones, so even a visible parent wouldn't have surfaced the urgency.

**Fix**: extracted the suppression rule — previously copy-pasted identically 3x, and the root of at least 3 separate bugs this session — into one shared `OAD.computeSuppressedChildUUIDs(childrenByParentUUID, activeByUUID, todayStr)` in `js/engine.js`. A child is now never suppressed if it's overdue or due today; suppression-into-a-nested-summary only applies to lower-urgency (future-dated) children, where a tidy rollup under the parent is a genuine improvement rather than a way to lose data. Removed the `overdueCount`/`overdueTag` badge and its CSS class (`.ds-child-overdue`) — dead code once suppressed children can no longer be overdue or due-today by construction. Four new unit tests (`computeSuppressedChildUUIDs: ...`) cover: normal suppression, due-today exemption, overdue exemption, and the Patient carve-out.

## OAD.Due — Single Source of Truth for "What's Due" (LIVE)
Origin: the child-suppression bug above and the two "This Week"/"Focus Now" bugs in parts 3-4 of the changelog were the same root cause recurring three times — "what's due" logic copy-pasted across `renderTodayView`/`renderDailyView`/`renderMatrixView`, plus a fourth, separate implementation in `selectFocusThread`/`selectFutureFocusSuggestion` that didn't even agree on suppression. `js/due.js` (`OAD.Due`) is the consolidation:

- **`OAD.Due.activeThreadsRaw()`** — status-filtered (`!= closed/dormant/inbox`), demo-role-scoped via `OAD.getVisibleThreads()`, **not** pressure-scored. Safe to call from inside `OAD.pressure()`'s own call chain.
- **`OAD.Due.activeThreads()`** — `activeThreadsRaw()` + `pressure()`-scored + sorted descending. This is the layer every rendering/ranking surface should use. **Never** call this from inside `OAD.pressure()` itself (see `getDayLoad` below) — it calls `pressure()` on every thread, which would recurse.
- **`OAD.Due.suppressionContext(activeThreads, todayStr, focusUUID, horizonStr)`** — builds `activeByUUID`/`childrenByParentUUID`, calls `OAD.computeSuppressedChildUUIDs()`, returns `visibleThreads`.
- **`OAD.Due.buckets(visibleThreads, todayStr, in7Str)`** / **`OAD.Due.cadenceBuckets(cadences, todayStr, in7Str)`** — the Overdue/Today/Week/No-Date split.
- **`OAD.Due.dashboardData(todayStr, in7Str)`** — the one call each render function makes: scores the active list once, derives the focus pick from that same scored list (via `OAD.getFocusUUID(active)`), then runs suppression + buckets. Returns `{ active, focusUUID, activeByUUID, childrenByParentUUID, suppressedUUIDs, visibleThreads, overdue, today, week, noDate }`.
- **`OAD.Due.selfCheck()`** — console-callable diagnostic against live data (`OAD.Due.selfCheck()`), checks: no suppressed child's parent is itself invisible (orphaned suppression — the deeper flaw the part-4 bug exposed), Focus Now's pick is never suppressed, no overdue-or-due-today thread is ever suppressed.

**Why `getDayLoad`/`calculateDayLoadScore` (`js/engine.js`) consume `activeThreadsRaw()`, never `activeThreads()`**: `OAD.pressure(thread)`, when not called with `_suppressSideEffects=true`, calls `OAD.getDayLoad(thread.next_action_date)` as part of its own scoring. If `getDayLoad` were built on `activeThreads()` (which calls `pressure()` unsuppressed on every thread to build its scored list), every top-level `pressure()` call would trigger a fresh full-backlog unsuppressed pressure pass via `getDayLoad`, each of which calls `getDayLoad` again — infinite recursion. `getDayLoad`/`calculateDayLoadScore` also now correctly exclude dormant/inbox threads and respect demo-role scoping, which they previously didn't (a real, if minor, pre-existing bug this consolidation fixed as a side effect).

**`selectFocusThread(activeThreads)` / `selectFutureFocusSuggestion(activeThreads)` / `getFocusUUID(activeThreads)`** (`js/engine.js`) all take an optional precomputed, pressure-scored active-thread list — defaulting to `OAD.Due.activeThreads()` when omitted, so every pre-existing zero-arg call site and test is unaffected. When given one, they filter/sort on the list's existing `_score` rather than recomputing `OAD.pressure()` a second time — this is what actually eliminates the redundant scoring pass, not just the parameter plumbing. `renderTodayView`/`renderDailyView`/`renderMatrixView` reconstruct their Focus Now card's thread via `due.active.find(t => t.uuid === due.focusUUID)` rather than calling `selectFocusThread()` again, so each render now pressure-scores the active backlog exactly once.

## Data Model — Deadline-Driven Prioritization (LIVE)

## Runway Risk — Convergence Check (LIVE, Steps 1/3/4 of the spec — Step 2 backfill deferred)
Spec: `flowqueue_runway_risk_spec.md`. A separate signal type from pressure/deadlineState — not "how urgent does this feel," but "given where things actually sit in the pipeline right now, is the trajectory even mathematically capable of landing before the deadline." Additive, read-only, never writes anything on its own.

- **`stage`** (Thread field, LIVE) — job-application pipeline stage: `null | applied | screening | interview | offer | rejected`. `null` by default on every thread; only meaningful on leaf application threads. Set via the "Job Application Tracking" section of the Edit Thread form. `OAD.APPLICATION_STAGES = ['applied','screening','interview','offer']` (ordered); `rejected` is a separate terminal value excluded from the ordering.
- **`OAD.Config.runwayBenchmarks`** (`js/config.js`, localStorage-backed like `lifeAreas`) — starting-assumption time-to-outcome per broad category, in weeks: `federal: 17-22`, `commercial: 6-8`. Adjustable, not derived from TJ's own data (sample size too small — 30+ applications, 0 hires as of this writing).
- **`OAD.calculateRunwayRisk(goalThreadId)`** (`js/engine.js`) — walks the goal thread's `enables` graph (goal → category threads classified Federal/Commercial by keyword → track threads → leaf application threads) using the same `getGraphContext()` traversal as everywhere else — no new grouping field needed, the existing graph structure already carries this. For each track, finds the earliest-active stage among its non-closed, non-rejected leaf applications (a track with **zero** applications is treated as the same worst case as "all applications still at applied," per the spec's own framing — not skipped). Estimates remaining weeks by linearly discounting the benchmark range by pipeline position (a stated simplification, not a real distribution). Flags `atRisk` using the benchmark's slower (max) estimate, and generates a plain-English sentence per track. Unclassifiable categories (title doesn't match "federal" or "commercial") are skipped, never guessed at.
- **Surfacing**: a `.runway-risk-card` on the goal thread's own detail view (`renderDetail`, mirrors the "Deadline Tracking" card) showing only at-risk tracks; and a global `#runway-risk-banner` (mirrors the overdue-Cadence banner's visual treatment, but wired into `_finishBoot()`/`refreshActiveView()` so it's genuinely persistent across view switches, not just visible on one panel). Both stay silent when nothing is at-risk.
- **Acknowledge / re-present (LIVE)** — per-track snooze, not a permanent dismiss: `track.runway_ack_until` (ISO date). `OAD.acknowledgeRunwayRisk(trackUuid)` (`js/data.js`) sets it to `today + OAD._RUNWAY_REPRESENT_DAYS` (7), logs an evolution entry, saves. `OAD._isRunwayRiskSnoozed(trackUuid)` (`js/render.js`) is a pure presentation-layer check — `calculateRunwayRisk()` itself stays unaware of acknowledgment and keeps reporting the true math; both the banner and the detail card filter snoozed tracks out until the date passes, at which point they reappear automatically if still genuinely at-risk (deadline math doesn't stop just because it was acknowledged once). "Acknowledge (1wk)" button on both surfaces.
- **Not done**: Step 2 of the spec (backfilling real `stage` values on TJ's ~18 live leaf application threads) was deliberately deferred — several thread titles (e.g. "VA GS-0028-9 Ineligibility — Follow Up") don't map cleanly to a pipeline stage from title alone, and the spec explicitly says not to guess. Until backfilled, every real leaf application defaults to `stage: null` → treated as `applied`, which is why both real Federal tracks currently show at-risk (conservative-by-default, not a bug).

## Time-of-Day Scheduling (LIVE)
Origin: static day-only pressure treated "meet Amy at 09:30" the same as a bill due in 5 months — technically correct date distance, wrong felt urgency. `next_action_date`/`deadline` were pure `YYYY-MM-DD` strings with no time granularity anywhere in the schema.

- **`next_action_time` / `deadline_time`** (Thread fields, optional `'HH:MM'` 24h, `null` = date-only) — set via the Edit Thread form and the Complete Action Wizard's "What's Next?" step.
- **`OAD._combineDateTime(dateStr, timeStr)`** (`js/engine.js`) — combines into a real local `Date`. No time set defaults to `23:59:59` of that date, which is what makes date-only threads behave exactly as before (not overdue until the calendar rolls to the next day). This is deliberately **local** time, not UTC — `<input type="date">`/`<input type="time">` values are inherently local wall-clock with no timezone info, and "is this overdue" must be judged against local now, not UTC now. (Watch for this in tests: `new Date().toISOString().slice(0,10)`, used throughout the rest of the codebase for `todayStr`, is UTC-based and can drift a day ahead of local during evening hours in negative-UTC-offset zones — don't use it to construct date-only test fixtures for time-aware logic; use a local-date constructor instead.)
- **`OAD.isActionOverdue(thread)`** / **`OAD.getOverdueDays(thread)`** (`js/engine.js`) — the single source of truth for "is this actually late right now," replacing ~15 duplicated `next_action_date < todayStr` string comparisons across `pressure()`, `focusReason()`, the three near-identical Daily View overdue-badge blocks, `getDailyToat()`'s friction detection, and Command Center. A thread with a specific time that passes today counts as **at least 1 day-equivalent overdue immediately** — a missed hard-time commitment shouldn't need to wait for midnight to register in pressure.
- **Not done**: the CIC/demo-role shift-collision system (`isOffDay`) and `dashboard.js`'s programmatic discharge-date setters were deliberately left untouched — different, unrelated features that happen to also read `next_action_date`.

## Pressure Score (engine.js)
OAD.pressure(thread) returns 0-100:
- stalled: +30, waiting: +15
- assumption unverified: +20
- critical: +30, high: +20, medium: +10
- contingency < 3 days: +25, < 7 days: +15, < 14 days: +5
- deadline within 7 days and not on track: +30
- deadline within 14 days and not on track: +20
- deadline within 30 days and not on track: +10
- behind by 2+ sessions: additional +15
- **cross-load multiplier: +12 when `getDayLoad(thread.next_action_date) > 150`** — surface threads piling up on the same day
- capped at 100
- **transitive blocking propagation (LIVE, July 2)**: a thread's final pressure is `max(its own score above, the highest pressure of anything currently blocking it)`, walking the full `blockedBy` closure (not just one hop) — cycle-safe via a visited-uuid guard. A thread blocked by an urgent prerequisite inherits that prerequisite's real pressure, not a discounted version of it. Replaces an earlier "bleed-up" mechanism that ran backwards (it boosted a *blocker's* pressure from what it blocked, not the reverse) and was capped at one hop — confirmed via a real-data audit (`fq-pressure-propagation-audit-2026`) that it silently understated blocked parent threads by up to 70 points.

## Cross-Load Awareness (engine.js)
`OAD.getDayLoad(dateStr)` — sums `pressure(t, true)` for all non-closed threads whose `next_action_date === dateStr`. The `_suppressSideEffects=true` flag prevents recursive calls into `getDayLoad` and skips redundant cycle-penalty checks (also used by `calculateCriticalPath`). It does NOT suppress transitive blocking propagation — that has its own `_visited`-based cycle guard and is expected to run at every hop so multi-hop chains propagate correctly. If the day's total load exceeds 150, each thread on that date gets +12 pressure. Implemented in `engine.js`; tested with a 3-thread stalled-critical fixture at date '2099-01-01'.

## This Week's Load — Composite Score (LIVE)
Origin: an investigation (`FLOWQUEUE_WEEKLY_LOAD_INVESTIGATION.md`) found the widget's Clear/Busy/Heavy label was driven purely by `itemCount + cadenceCount` — any day with 1+ item was unconditionally "Heavy," no matter how light. TJ's framing: "I could have 10 easy tasks and be Busy, but two tasks and be Underwater" — count alone can't distinguish those.

- **`OAD.calculateDayLoadScore(dateStr)`** (`js/engine.js`) — a *separate* function from `getDayLoad()` (which must stay a pure pressure-sum feeding `pressure()`'s own cross-load multiplier, to avoid a new feedback loop). Composite = `getDayLoad(dateStr)` (pressure-sum, reused) + `edgeSum * edgeMultiplier` (total graph-connection degree — in+out, all edge types — for threads due that day; a proxy for coordination/complexity deliberately distinct from urgency, since pressure already reflects urgency inherited *through* blocking chains but not raw entanglement of any type) + `cadenceCount * cadenceWeight` (cadences have no pressure score of their own).
- **`OAD.getDayLoadLabel(score)`** (`js/engine.js`) — maps the composite score to `clear`/`busy`/`heavy` using configurable thresholds.
- **`OAD.Config.weekLoadWeights`** (`js/config.js`, localStorage-backed like `lifeAreas`/`runwayBenchmarks`) — `{ edgeMultiplier: 2, cadenceWeight: 20, busyThreshold: 50, heavyThreshold: 150 }`. Golden rule: no magic numbers in the code — every weight/threshold lives here, adjustable without a code change. Starting defaults, not derived from a large sample — tune as the labels are compared against how days actually feel.
- **Deliberately deferred**: a "scope" term (thread size/effort) was considered and dropped for now — checked the real export first: only 5 of 269 threads have `effortEstimate` set at all (2 have `weeklyCommitment`), too sparse to weight meaningfully. Revisit once there's an actual workflow around setting those fields.
- **Bug 1 (stale count) root cause**: nothing in the app re-checks view accuracy without an explicit mutation — a tab left running constantly (confirmed usage pattern: FlowQueue stays open in its own workspace) can show a render from before items rolled into "today." Fixed with `OAD._autoRefreshActiveView()` (`js/render.js`) wired to `visibilitychange` (immediate, on tab focus regain) plus a 5-minute periodic safety net (in case workspace-switching doesn't fire the event) — both skip refreshing while a thread detail is open (`OAD._activeId` set), so they don't yank a page out from under someone mid-read. ## Export / Import (LIVE)
Located in `js/data.js` and `js/modals.js`. Accessible from the Settings modal.

### Export (`OAD.exportThreads()`)
Moat-safe flat JSON. Includes basic thread attributes (uuid, parent_uuid, title, status, priority, life_area, pressure, closing_condition, next_action, next_action_date, etc.). Calls `_normalizeDB()` + `saveDB()` before building the payload so UUID backfill is always complete.

**Includes:** per-thread `connections[]` (full edge metadata), top-level `edges[]` (flat list of all edges), `edge_count`, `deleted_edge_uuids: []`.

**Deliberately excludes:** evolution_log, current_assumption, contingency_action, contingency_escalation, ai_insights[], and persona data.

Includes `exported_by: user_id` — ownership-stamped for future multi-user scoping.

### Import (`OAD.parseImportFile()` + `OAD.applyImport()`)
Accepts the same JSON format. Matching priority: **(1)** UUID match — `row.uuid` finds existing thread → update; **(2)** title fallback — `row.uuid` absent/null AND exactly one non-closed thread shares the title → update (prevents duplicates from AI-generated patches and older export formats that omit UUIDs); **(3)** create — neither matched. Title fallback is deliberately conservative: if two open threads share the same title, the row falls through to create rather than risk updating the wrong one.

**`_IMPORT_FIELDS`** controls which fields sync on update. `title` and `date_push_count` are included. The `_diffImportItem` preview shows title changes before the user confirms.

- Row with UUID matching an existing thread → staged as update (shows field-by-field diff, requires per-item checkbox confirmation)
- Row with unknown or absent UUID → create
- Evolution log is always appended, never overwritten; deduped by date+note

`applyImport()` re-looks up each thread by UUID at apply time, not from stored references, to avoid stale-reference bugs. Returns `{ created, updated, closed, edges_merged }`. Processes `deleted_edge_uuids` and merges top-level `edges[]` into thread `connections[]`.

## Auto-Dependency Engine (ADE) — LIVE
Located in `js/engine.js`. Runs automatically at boot via `_finishBoot()` and after every import.

### Key Data
- `OAD.DB.ade_suppressions[]` — `{from_uuid, to_uuid, rule}` pairs. Edges in this list are never re-created by ADE. Populated when user rejects an ADE suggestion.
- Per-thread `connections[]`: ADE-inferred edges have `auto_generated: true`, `confirmed_by_user: false` until user reviews.

### Three Rules
- **ADE-001** `_ade001_sequential()` — Groups open threads by course prefix (`^(.*?)\bWeek\s+(\d+)\b`). Creates `Week N → blocks → Week N+1` (consecutive only). Finals (`\b(final exam|finals|final)\b`) blocked by all weeks in the group. Confidence: 0.97.
- **ADE-002** `_ade002_parentChild()` — For every thread with `parent_uuid`: parent `enables` child. Confidence: 1.0.
- **ADE-003** `_ade003_sharedIdentifier()` — Extracts shared identifier (`\b([A-Z]{2,5}[-\s][A-Z0-9]{2,})\b`) from titles. Prep verbs (build/draft/prepare/review/create/write/complete) block submit verbs (submit/apply/send/deliver/file/upload). Confidence: 0.92.

### Key Functions
- `OAD._adeAddEdge(from, to, edgeType, rule, confidence)` — checks suppressions + dedup before creating; returns bool
- `OAD.runADE()` — runs all three rules, calls `saveDB()` if any edge created, returns total count
- `OAD.confirmEdge(threadId, edgeUuid)` — sets `confirmed_by_user: true` on edge
- `OAD.rejectEdge(threadId, edgeUuid)` — removes edge from thread, adds to `ade_suppressions`

### UI
- Graph card in detail view: "N pending" badge when unconfirmed ADE edges exist; "⚡ Review AI suggestions" button
- `OAD.openGraphIntelligencePanel(threadId)` in `js/modals.js` — shows each unconfirmed edge with Confirm/Reject buttons
- Rejecting an edge suppresses it permanently (won't re-appear unless suppression is manually removed)

## Data Model — Cadence (LIVE)
Cadences are date-anchored mandatory obligations that recur on a known schedule. The date IS the work. Missing a Cadence is a failure state.

Every cadence has:
- id, title, life_area
- recurrence — monthly-1st | monthly-15th | monthly-last | weekly | weekly-days | custom (`custom` is in the enum but has no `nextCadenceDue`/`prevCadenceDue` branch — unimplemented)
- days_of_week[] — only used when recurrence is `weekly-days`; integers 0–6 matching `Date.getDay()` (0 = Sun). Backfilled to `[]` by `_normalizeDB()` for cadences that predate this field.
- last_completed (date), next_due (date), overdue (boolean)
- notes, consequences

`OAD.nextCadenceDue(recurrence, fromDate, daysOfWeek)` and `OAD.prevCadenceDue(recurrence, daysOfWeek)` in `engine.js` compute the schedule. For `weekly-days`, next-due walks forward from the day *after* `fromDate` to the nearest matching weekday (so completing on a day that's itself in the list rolls to the following week, not the same day); prev-due walks backward from today inclusive. Both fall back to `null`/plain-weekly behavior if `days_of_week` is empty. `OAD.formatRecurrence(c)` expands `weekly-days` into a sorted day-name label (e.g. `weekly-days (Mon, Wed, Fri)`) for display; the cadence edit form exposes day checkboxes via `.cd-dow`.

3 seed cadences: Pay the Bills (1st), Pay the Bills (15th), and Monthly Bills Review (monthly-15th). Seeding is done by `OAD._seedCadences()` in `tests/tests.data.js` — extracted from `_seedData()` so it can be called independently in the `_bootAfterAuth` guard block.

UI behavior:
- Cadences panel — click "Cadences" in the header nav
- Overdue cadences surface as a hard banner in the detail panel
- Completed cadences show ✓; reset automatically on next trigger date
- No pressure score — binary: done or not done

## Data Model — Saved View / Graph Views (LIVE)
Named, persisted filter+sort predicates over the thread list, stored in `OAD.DB.saved_views[]` (rides the same whole-DB JSONB blob as everything else — no schema/Supabase changes needed). FlowQueue's answer to Super Productivity's "Boards," but able to filter on graph-edge conditions SP structurally can't express (no dependency concept in SP's data model).

Every saved view has:
- id, name
- statuses[], priorities[], life_areas[] — include-lists; empty array = no restriction (matches everything), not "match nothing"
- edge_rule — `null`, or `{ type: 'blocked_by_open' | 'has_blocks' | 'no_blockers' }`. Fixed enum, not a query DSL — evaluated in `OAD.matchesSavedView()` (`engine.js`) by reusing `OAD.getGraphContext()`, the existing bidirectional edge-resolution helper.
- sort_field (`pressure` | `deadline` | `next_action_date` | `title`), sort_dir (`asc` | `desc`)

Key functions:
- `OAD.matchesSavedView(thread, view)` / `OAD.applySavedView(threads, view)` (`engine.js`) — pure filter+sort, no DOM
- `OAD.addSavedView` / `getSavedView` / `updateSavedView` / `deleteSavedView` (`js/data.js`) — CRUD, mirrors Cadence pattern
- `OAD.openManageSavedViewsModal` / `openNewSavedViewModal` / `openEditSavedViewModal` (`js/modals.js`) — create/edit/delete UI

UI behavior:
- Lives inside the existing List Tab (`OAD.renderListView()`/`filterListTab()`, `js/render.js`) — no new nav panel. A "— No Saved View —" selector plus "Manage Views" button sit in the list toolbar; selecting a view supersedes the ad hoc status filter (disabled while a view is active) and composes with the free-text search box, same as SP's board+search interaction.
- No Kanban/column UI — a saved view renders as a filtered, sorted list, consistent with how the rest of FlowQueue presents threads.

## Quick Add / Inbox Capture (Part 1 — LIVE; Parts 2-4 not yet built)
Spec: `flowqueue_quickadd_inbox_spec.md`. Design principle: automation is safe in proportion to how fast a human can see and undo it — Part 1 does zero synthesis, zero LLM calls, and writes nothing but the raw capture itself.

- **UI**: single always-available text input in the `<header>` (`#quick-add-input`, between the brand mark and nav actions), not the header nav or a modal — the one piece of chrome visible regardless of active view. Enter submits. Starts `disabled` in the static HTML; `OAD._enableQuickAdd()` (called from `_finishBoot()`) enables it once `OAD.DB` is the real, cloud-loaded object — enabling it earlier risks a capture landing in a pre-auth placeholder DB that `_bootAfterAuth()` discards when it replaces `OAD.DB` wholesale.
- **`OAD.quickAddThread(rawText)`** (`js/data.js`) — trims input, rejects empty/whitespace-only (returns `null`), creates a minimal thread via `makeThread({title, status: 'inbox'})`, logs one evolution entry ("Captured via Quick Add."). Fully synchronous — no LLM call blocks the save.
- **`OAD.submitQuickAdd()`** (`js/render.js`) — reads `#quick-add-input`, calls `quickAddThread()`, clears the field, briefly flashes a `.quick-add-saved` success state, calls `refreshActiveView()`.
- **Inbox nav (LIVE)** — `OAD.renderInboxPanel()` (`js/render.js`), under header nav → Queues → Inbox. One click into the existing List Tab pre-filtered to `status=inbox` (`OAD._activeListStatus = 'inbox'` then `renderListView()`) — not a new panel type, reuses List Tab's search/cards/sort as-is. Added after first real usage surfaced that Quick Add had no way to find what you'd just captured except manually searching List. `'inbox'` is also a selectable option in the List Tab's own status dropdown.
- **Not yet built** (spec Parts 2-4, intentionally deferred until the capture habit proves out): capture-time keyword/life_area suggestions, a dedicated Housekeeping Review screen listing all `inbox` threads with `date_push_count`-based threshold flagging, and the clarify-then-propose synthesis flow that turns a reviewed inbox item into real graph structure (new threads/edges) with explicit approval before writing — should reuse the import diff-preview pattern (`_diffImportItem`) rather than invent a new approval UI.

## Calendar Sync & OAuth SSO
- **OAuth Providers:** Google (`google`) and Microsoft (`azure`) are implemented in the `OAD._signInWithProvider` flow (`js/modals.js`).
- **Scopes Requested:** 
  - Google: `https://www.googleapis.com/auth/calendar.readonly`
  - Microsoft: `Calendars.Read`
- **Security:** Access tokens are secured and provided via `supabase.auth.getSession()` session metadata, preparing the application to safely pull down calendar events.
